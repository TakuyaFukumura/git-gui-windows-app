# Git GUI Windows App リファクタリング計画書

## 1. 目的

本計画は、現在のJavaFXアプリケーションの挙動を維持しながら、内部構造を段階的に整理するための実施順序と完了条件を定める。

現状は、`GitGuiWindowsApp`に画面構築、画面状態、非同期実行、Git操作の結果処理、ダイアログ表示が集中している。一方、Git実行基盤、出力パーサー、モデル、設定管理は個別クラスに分離されている。

リファクタリングでは、機能追加を同時に行わず、各段階でコンパイルと既存テストを通過させる。ユーザーが認識できる動作、Gitコマンドの安全な引数分離、設定ファイルの互換性を維持する。

## 2. 対象範囲と制約

### 2.1 対象

- `GitGuiWindowsApp`の責務分割
- Git操作サービスと非同期実行の整理
- 画面状態と表示更新の一元化
- モデル、パーサー、設定管理の境界明確化
- テスト容易性とテストデータの改善
- パッケージ構成と命名の整理

### 2.2 対象外

- リモート操作（fetch、pull、push）
- マージ、コンフリクト解決、rebaseなどの新機能
- UIデザインの刷新
- FXML導入やDIフレームワーク導入
- Gitコマンド仕様の変更
- 設定ファイル形式や保存場所の変更

### 2.3 守るべき不変条件

- Gitコマンドはシェルを介さず、引数リストで実行する。
- リポジトリ選択、status、diff、stage、unstage、commit、branch操作、履歴表示の挙動を変えない。
- 未コミット変更があるブランチ切替の確認と、現在・未マージブランチの削除防止を維持する。
- Git操作の失敗を成功として表示しない。
- `%USERPROFILE%\.git-gui-windows-app\settings.properties`を既存利用者が読み込める状態に保つ。
- 各段階で既存のヘッドレステストを実行できる状態にする。

## 3. 現状の構造と主な課題

```text
GitGuiWindowsApp
  ├─ JavaFXレイアウトとコントロール生成
  ├─ リポジトリ・ブランチ・履歴の画面状態
  ├─ Task/Threadによる非同期実行
  ├─ 成功・失敗時の画面更新
  ├─ 確認・エラーダイアログ
  └─ GitServiceの呼び出し

GitService
  ├─ Gitコマンドの組み立て
  ├─ リポジトリ検証
  ├─ status/diff/branch/commit履歴取得
  └─ stage/unstage/commit/branch操作

GitCommandRunner / 各Parser / model / ApplicationSettings
```

主な課題は次のとおりである。

- 1つの画面クラスが大きく、レイアウト変更と操作ロジックが密結合している。
- 非同期処理の開始、Busy状態、エラー表示、再読み込みが各操作に分散している。
- `repository`、`repositoryInfo`、ブランチ一覧、履歴一覧などの状態が画面クラスのフィールドに直接保持されている。
- `GitService`が読み取り、変更操作、履歴取得、ブランチ操作を一つのサービスに集約している。
- UIからテストしにくい判断ロジック（選択状態、ボタン有効条件、履歴絞り込み）が画面クラスに含まれている。

## 4. 進め方の原則

1. 先に現状の挙動をテストで固定し、その後に構造だけを変更する。
2. 1ステップ1責務を基本とし、各ステップを独立したコミットにできる大きさにする。
3. 公開APIを一度に変更せず、呼び出し側を移行してから不要なAPIを削除する。
4. UIとGit操作の間に新しい境界を設け、JavaFX依存を下位層へ持ち込まない。
5. 構造変更と機能変更を同じコミットに混ぜない。
6. 各段階の終了時に`mvnw.cmd clean install`または`mvn clean install`を実行する。

### Step 0: ベースラインを固定する

**目的**

**作業内容**

- `GitService`の各公開メソッドと対応するGitコマンドを一覧化する。
- 現在の設定キー、既定値、保存先を確認する。
- 既存テストを実行し、ベースラインの結果を記録する。
- 足りない回帰テストを、構造変更前の実装に対して追加する。

**完了条件**

- status、diff、stage、unstage、commit、branch、history、settingsの主要経路を確認できる。
- 既存テストが成功する。
- 以降のステップで守るべき挙動と非互換変更を明文化できる。

**検証**

```cmd
mvnw.cmd clean install
```

### Step 1: パッケージと依存方向を整理する

**目的**

UI、アプリケーション制御、Gitインフラ、設定、モデルの依存方向を明確にする。

**作業内容**

- `app`または`application`層を追加し、画面から呼び出すユースケースの境界を定義する。
- `ui`層を画面表示とユーザー入力の受け取りに限定する。
- `git`層はGit実行、パース、Git操作の結果だけを担当する。
- `model`層はJavaFX型やファイル入出力に依存しないことを確認する。
- `config`層は設定の読み書きと値の検証に限定する。
- 循環依存が発生しないよう、依存関係を文書化する。

**完了条件**

- `model`からJavaFXクラスを参照しない。
- UI以外のクラスから画面コントロールを参照しない。
- パッケージ移動後も機能とテストが変わらない。

**検証**

- `mvnw.cmd clean test`
- パッケージ間のimportを確認する。

### Step 2: 画面状態を`AppState`へ集約する

**目的**

画面クラスに分散しているリポジトリ、変更、ブランチ、履歴、Busy状態を明示的な状態モデルへ移す。

**作業内容**

- `repository`、`repositoryInfo`、ブランチ一覧、履歴一覧、履歴検索条件、操作状態を状態クラスにまとめる。
- `未選択`、`読み込み中`、`利用可能`、`操作中`、`エラー`の状態を表現する。
- 状態更新を一方向に行う小さな更新メソッドを用意する。
- JavaFXの`TableView`や`ListView`を状態モデルに持ち込まない。
- 既存の表示文言とボタン無効条件を維持する。

**完了条件**

- 画面クラスが複数の状態フィールドを個別に書き換えない。
- ボタンの有効条件を状態から再計算できる。
- 履歴検索などの純粋な変換処理をUIから分離できる。

**検証**

- 状態遷移とボタン条件の単体テストを追加する。
- 既存のJavaFX画面でリポジトリを開き、更新・操作後の表示を確認する。

### Step 3: Git操作の実行制御を`OperationCoordinator`へ分離する

**目的**

非同期タスク、Busy状態、成功・失敗処理、スレッド管理を一箇所に集約する。

**作業内容**

- `Task`生成、デーモンスレッド作成、例外変換を専用クラスへ移す。
- 操作名、進行中表示、成功時の再読み込み、失敗時のエラー通知を統一する。
- 同時実行防止をUIコントロール単位ではなく操作制御単位で行う。
- `InterruptedException`の割り込み状態を維持する。
- Gitエラーと予期しないエラーを区別して上位へ通知する。

**完了条件**

- `GitGuiWindowsApp`に直接の`new Task`、`new Thread`が残らない。
- すべてのGit操作が同じ成功・失敗経路を通る。
- 操作中の更新、履歴更新、ステージ操作が二重実行されない。

**検証**

- `GitCommandRunnerTest`、`GitServiceTest`を実行する。
- Git実行失敗、割り込み、リポジトリ未選択の経路を確認する。

### Step 4: 画面を機能単位のView/Controllerへ分割する

**目的**

画面構築と機能ごとのイベント処理を分離し、変更範囲を小さくする。

**作業内容**

- リポジトリ・ブランチ操作を`RepositoryToolbar`相当のクラスへ移す。
- 変更一覧と差分表示を`ChangesPane`へ移す。
- ステージ・アンステージ・コミットを`CommitActionBar`へ移す。
- 履歴検索、履歴一覧、詳細を`HistoryPane`へ移す。
- ダイアログの共通スタイルと生成処理を`DialogService`へ移す。
- 各ViewはGitServiceを直接呼ばず、アプリケーション層の操作を呼び出す。
- FXMLや外部フレームワークは導入せず、既存のJavaFXコードによる構築を維持する。

**完了条件**

- `GitGuiWindowsApp`はStage、Scene、全体レイアウトの組み立てとライフサイクル管理に限定される。
- 機能別クラスが互いのJavaFXコントロールを直接操作しない。
- 既存の最小ウィンドウサイズ、テーマ、タブ構成、表示文言を維持する。

**検証**

- 起動、リポジトリ選択、変更表示、履歴表示を手動確認する。
- `mvnw.cmd clean install`を実行する。

### Step 5: `GitService`を用途別のFacadeへ分割する

**目的**

読み取り操作と変更操作の責務を分け、Gitコマンド追加時の影響範囲を抑える。

**作業内容**

- `RepositoryService`: リポジトリ検証、status、HEAD取得。
- `ChangeService`: diff、stage、unstage。
- `BranchService`: 一覧、作成、切替、削除、ブランチ名検証。
- `HistoryService`: commit履歴と参照情報の取得。
- `CommitService`: コミット実行とコミットID取得。
- 共通の`GitCommandRunner`、例外、結果モデルは再利用する。
- 移行中は既存`GitService`をFacadeとして残し、呼び出し側を段階移行してから削除を検討する。

**完了条件**

- 各Facadeが担当領域外のGitコマンドを実行しない。
- Git引数の分離、`--`によるパス境界、エラー処理を維持する。
- UIから用途別Facadeまたはアプリケーション層を経由して操作する。

**検証**

- 各Facadeのサービス単体テストを追加する。
- 一時Gitリポジトリでstatus、diff、stage、unstage、commit、branch、historyを確認する。

### Step 6: Parserとモデルの境界を強化する

**目的**

Git出力形式への依存箇所を限定し、モデルの意味を明確にする。

**作業内容**

- `GitStatusParser`、`GitDiffParser`、`GitBranchParser`、`GitCommitParser`の入力と出力契約を整理する。
- Git出力の区切り文字、空入力、文字コード、異常形式に対する扱いを統一する。
- UI表示用の文字列生成をParserから除外する。
- `StageState`、変更種別、参照種別などの状態の組み合わせを整理する。
- 不変モデルのnull許容範囲と空コレクションの方針を明文化する。

**完了条件**

- ParserはJavaFXに依存せず、入力文字列からモデルを返す。
- 不正なGit出力を黙って成功扱いしない。
- UI用の表示文言がParserに混在しない。

**検証**

- 正常、空、特殊文字、バイナリ、巨大差分、複数親コミットのテストを追加する。
- `mvnw.cmd clean test`を実行する。

### Step 7: 設定とテーマ適用を分離する

**目的**

設定ファイルの永続化とJavaFXのテーマ適用を切り分け、設定変更時の影響を限定する。

**作業内容**

- `ApplicationSettings`の読み書きと値検証を設定リポジトリ相当のクラスへ分離する。
- 設定の既定値を一箇所に集約する。
- ウィンドウ状態、Git実行ファイル、最近のリポジトリ、基準フォルダーをカテゴリ別に扱う。
- テーマ切替とCSS適用を`ThemeService`相当へ移す。
- 壊れた設定値、保存失敗、親ディレクトリ作成失敗の扱いを維持する。

**完了条件**

- 設定の読み書きをJavaFXなしでテストできる。
- 既存の設定ファイルを読み込める。
- 起動時復元と終了時保存の挙動が変わらない。

**検証**

- `ApplicationSettingsTest`を実行する。
- 一時ファイルで既定値、破損値、重複した最近のリポジトリ、保存失敗を確認する。

### Step 8: テスト構成を整理してリファクタリングを完了する

**目的**

今後の機能追加で構造が再び一つのクラスへ戻らないようにする。

**作業内容**

- テストを`config`、`git`、`application`、`model`の責務に対応するパッケージへ整理する。
- 一時Gitリポジトリ生成の共通Fixtureを作成する。
- Git実行を差し替え可能なテスト用境界を整備する。
- UIから分離できる判断ロジックをすべてヘッドレステストへ移す。
- READMEのプロジェクト構成と本計画書の完了状況を更新する。
- 未使用クラス、旧Facade、重複ヘルパーを削除する。

**完了条件**

- 構造変更後の全テストが成功する。
- 主要なGit操作と設定処理に回帰テストがある。
- `GitGuiWindowsApp`がアプリケーションの配線とJavaFXライフサイクルに集中している。
- 未使用の旧クラスや移行用コードが残っていない。

**検証**

```cmd
mvnw.cmd clean install
```

GUI環境では、リポジトリ選択、変更・差分、ステージ、コミット、ブランチ操作、履歴検索、テーマ切替、終了時保存を一通り手動確認する。

## 6. ステップごとのコミット方針

各ステップは、次のような独立したコミットに分ける。

1. `Add refactoring baseline tests`
2. `Organize application package boundaries`
3. `Introduce application state model`
4. `Extract Git operation coordinator`
5. `Split JavaFX views by feature`
6. `Separate Git operation facades`
7. `Strengthen parser and model boundaries`
8. `Separate settings and theme services`
9. `Complete refactoring test cleanup`

コミットには機能変更を混在させず、各コミット後に対象テストを実行する。途中段階でもビルド可能な状態を保ち、問題が発生した場合は直前の構造まで安全に戻せるようにする。

## 7. リスクと対策

| リスク | 対策 |
|---|---|
| UI分割時にイベントの接続が外れる | 機能単位に移動し、各移動直後に起動と操作を確認する |
| 非同期処理の例外が画面に届かなくなる | 成功・失敗・割り込みを共通Coordinatorのテストで固定する |
| Git引数の意味が変わる | 既存テストを先に固定し、コマンド配列を比較するテストを維持する |
| 設定ファイルを読めなくなる | 既存キーと保存先を変更せず、旧形式の読み込みテストを追加する |
| リファクタリングが機能追加に膨張する | 各Stepの対象外を守り、仕様変更は別の計画・コミットに分ける |
| 大きな一括移動でレビュー不能になる | 1責務1ステップ、移動と命名変更を小さく分ける |

## 8. 完了判定

以下をすべて満たした時点で本計画を完了とする。

- 全ステップの完了条件を満たしている。
- `mvnw.cmd clean install`または`mvn clean install`が成功する。
- 現行機能の手動確認で、リファクタリング前後の挙動差がない。
- Gitコマンドの安全な引数分離が維持されている。
- 既存設定ファイルを読み込める。
- READMEとソースのパッケージ構成が一致している。
- 未使用の移行コード、重複処理、不要な互換Facadeが削除されている。
